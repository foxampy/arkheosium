# Регламент работы UNICAP.Lab

**Шифр документа:** UNICAP-REG-ULAB-001
**Статус:** проект · подлежит утверждению
**Владелец:** Governance & Legal
**Основание:** устав UNICAP.Lab (UNICAP-CHR-ULAB-001)

---

## Назначение

Устав отвечает на вопрос «что и кем устроено». Регламент отвечает на вопрос «в каком порядке это делается». При расхождении между документами применяется устав.

---

## 1. Открытие темы

**1.1.** Тема открывается решением председателя по представлению руководителя направления.

**1.2.** Представление содержит семь позиций. Отсутствие любой из них — основание вернуть представление:

| № | Позиция | Чем проверяется |
|---|---|---|
| 1 | Предмет исследования или разработки | формулировка, допускающая проверку |
| 2 | Направление по разделу 4 устава | ссылка на пункт |
| 3 | Ответственная роль | название роли, не организации |
| 4 | Базовая линия | описание состояния «до» и способа его измерения |
| 5 | Показатели результата | для каждого — способ измерения |
| 6 | Контур финансирования | один из трёх, по п. 8.1 устава |
| 7 | Кому принадлежит результат | по разделу 9 устава |

**1.3.** Теме присваивается шифр. Порядок присвоения — раздел 4 настоящего регламента.

**1.4.** Тема без базовой линии не открывается. Это правило не имеет исключений: сравнивать результат будет не с чем.

---

## 2. Стадии работы

| Стадия | Содержание | Условие перехода к следующей |
|---|---|---|
| Заявлена | тема сформулирована | представление принято по п. 1.2 |
| Открыта | назначен ответственный, присвоен шифр | утверждена программа работ |
| В работе | ведутся наблюдения, расчёты, разработка | получены первичные результаты |
| На проверке | результаты сверяются по разделу 7 устава | проверка пройдена |
| Оформлена | документ подготовлен | пройдено рецензирование |
| Закрыта | результат принят либо тема прекращена | решение с указанием причины |

**2.1.** Прекращение темы оформляется решением с причиной. Молчаливое прекращение не допускается: тема, по которой год не велось работ и нет решения о прекращении, выносится на научный совет.

**2.2.** Возврат темы на предыдущую стадию допускается и не считается неудачей. Проведение темы через стадию без выполнения условия перехода — считается.

---

## 3. Статусы документов

| Статус | Что означает | Публичность |
|---|---|---|
| не написан | тема в реестре, текста нет | запись видна, документ недоступен |
| черновик | текст есть, проверка не пройдена | закрыт |
| альфа | проверка величин пройдена, возможны изменения | открыт со статусом |
| на рецензии | передан рецензентам | открыт со статусом |
| утверждён | принят председателем либо научным советом | открыт |

**3.1.** Статус показывается рядом с документом во всех оболочках. Документ в статусе «альфа», представленный как утверждённый, — нарушение п. 7.7 устава.

**3.2.** Перевод в статус «утверждён» без прохождения рецензирования невозможен.

---

## 4. Шифры

**4.1.** Шифр документа: `UNICAP-<ТИП>-<ОБЛАСТЬ>-<НОМЕР>`.

| Тип | Расшифровка |
|---|---|
| CHR | устав |
| REG | регламент |
| JUR | юрисдикция |
| WPR | whitepaper |
| DIS | диссертация, научная работа |
| GRT | грантовый документ |
| RDM | дорожная карта |
| FIN | финансовый документ |
| PRS | презентация |

**4.2.** Шифры исследовательских тем:

- **D1–D21** — водно-экологический контур UNICAP;
- **Z1–Z21** — ветеринарно-экологический контур лаборатории.

**4.3.** Пространства не пересекаются. Упоминание диапазона целиком («D1–D21») допускается в любом документе — это ссылка на пространство, а не на тему. Употребление шифра чужого контура в качестве темы проверяется программно и является ошибкой сборки.

**4.4.** Шифр не переиспользуется. Освободившийся после закрытия темы шифр остаётся за закрытой темой навсегда.

---

## 5. Проверка величин

**5.1.** До передачи документа на рецензирование каждая числовая величина относится к одному из трёх уровней по п. 7.1 устава и помечается.

**5.2.** Порядок проверки:

1. выписать все величины документа;
2. для каждой указать источник;
3. величины без источника перевести в параметры модели;
4. для параметров модели провести анализ чувствительности;
5. заменить точечные утверждения, опирающиеся на параметры, диапазонами.

**5.3.** Документ, в котором хотя бы одна величина не отнесена к уровню, на рецензирование не принимается.

**5.4.** Источники, признанные недостоверными, вносятся в перечень запрещённых к использованию с указанием причины. Величина из такого источника не применяется даже со ссылкой.

---

## 6. Рецензирование

**6.1.** Рецензент не может быть автором документа и не может находиться в подчинении у автора.

**6.2.** Рецензия отвечает на пять вопросов:

1. следует ли вывод из состава работ;
2. отнесены ли величины к уровням достоверности;
3. описан ли способ измерения каждого показателя;
4. заявлена ли базовая линия;
5. обоснована ли устойчивость результата без ссылки на будущее финансирование.

**6.3.** Отрицательный ответ на любой вопрос возвращает документ автору с письменным изложением причины.

**6.4.** Рецензия хранится вместе с документом.

---

## 7. Публикация в Библиотеке

**7.1.** Порядок ввода документа в корпус:

1. файл помещается в `docs/`;
2. запись вносится в `registry.cjs` с указанием шифра, названия, категории, статуса, владельца и перечня оболочек;
3. выполняется `node build.cjs` — манифест собирается программно;
4. выполняется `node smoke.cjs` — проверка сходимости и разведения шифров;
5. выполняется `node sync.cjs` — раздача в оболочки;
6. оболочки разворачиваются.

**7.2.** Размеры, число строк и контрольные суммы вычисляются с диска. Вписывание этих величин вручную запрещено: манифест, заполненный руками, перестаёт быть проверкой.

**7.3.** Файл в `docs/`, отсутствующий в реестре, останавливает сборку. Это не неудобство, а защита корпуса от бесконтрольного пополнения.

**7.4.** Раздача односторонняя. Правка документа в оболочке недопустима: она будет затёрта ближайшей синхронизацией и потеряна.

**7.5.** Изъятие документа: сначала решение с причиной, затем удаление записи из реестра, затем синхронизация, которая удалит файл из оболочек.

---

## 8. Участники

**8.1.** Заявка подаётся через анкету онбординга. Анкета собирает: идентификацию, контакты, характер участия, департамент, роль, квалификацию, компании, кампании и проекты участия.

**8.2.** Заявка проверяется. Проверяются: непротиворечивость сведений, наличие подтверждений заявленной квалификации, отсутствие нераскрытого конфликта интересов.

**8.3.** DAO ID присваивается решением по итогам проверки. Подача анкеты учётной записи не создаёт.

**8.4.** Учёные степени вносятся только при наличии диплома с указанием его реквизитов. Заявленная без диплома степень в реестр не вносится и в публичных материалах не указывается.

**8.5.** Роль участника едина во всех оболочках: справочник ролей и департаментов ведётся в контуре DAO, оболочки его потребляют.

---

## 9. Отчётность

**9.1.** Периодичность: месячный обзор состояния тем, квартальный отчёт по направлениям, годовой отчёт лаборатории.

**9.2.** Отчёты об одних и тех же работах разным адресатам строятся из одного набора данных. Расхождение между ними — нарушение п. 7.7 устава, а не особенность подачи.

**9.3.** Годовой отчёт раздельно показывает **действующие** и **заявленные** направления по п. 4.18 устава.

---

## 10. Конфликт интересов

**10.1.** Раскрытие производится до обсуждения вопроса, а не после принятия решения.

**10.2.** Раскрытие фиксируется письменно и хранится с материалами вопроса.

**10.3.** Решение, принятое при нераскрытом конфликте, пересматривается по требованию любого участника научного совета.
