# ARKHEOSIUM — План создания настоящих 3D-моделей объектов и проектов (Цифровые двойники)

Дата: 2026-07-16
Маршрут-заготовка: `/hub/object/:id/twin` (`DigitalTwinPage` — сейчас заглушка).
Стек-пины (НЕ бампать): `three@0.170.0`, `@react-three/fiber@^8`, `@react-three/drei@^9`.

> Цель (по запросу): настоящие высокополигональные и точные 3D-модели объектов и проектов — полупрозрачные станции/сооружения, внутри которых можно рассматривать реальное оборудование и технологии; видно, как всё связано, работает и функционирует; на моделях можно заменять оборудование/технологии и видеть эффекты (на индексы, стоимость, производительность).

---

## 1. Концепция: «Прозрачный двойник»

Каждый объект (водоочистная станция, насосная, дамба, канал) — это 3D-сцена из трёх слоёв, переключаемых пользователем:

1. **Оболочка (Shell)** — здание/сооружение. Режимы: непрозрачный → полупрозрачный (`transmission`/opacity) → «разрез» (clipping plane) → скрытый каркас (wireframe).
2. **Оборудование (Equipment)** — внутренние узлы: насосы, мембраны RO, UF/MBR-модули, фильтры, резервуары, трубопроводы, датчики, SCADA-шкафы. Каждый — кликабельный, с карточкой характеристик.
3. **Потоки и связи (Flows)** — анимированные потоки воды/энергии/данных по трубам и кабелям (частицы вдоль кривых), показывающие как всё функционирует.

Пользователь: вращает сцену → делает оболочку полупрозрачной → кликает на насос → видит характеристики → **выбирает замену** (другая технология/модель) → пересчёт эффектов (производительность ↑, энергопотребление ↓, стоимость, влияние на индексы благополучия/экологии) → визуальное изменение узла и потоков.

## 2. Архитектура данных (модель-агностик)

Модели описываются данными, а сцена собирается процедурно из «спецификации оборудования». Это позволяет заменять узлы без правки 3D-файлов.

```ts
// src/data/twin/types.ts
type EquipmentCategory =
  | 'pump' | 'membrane_ro' | 'membrane_uf' | 'mbr' | 'filter_sand'
  | 'clarifier' | 'uv_reactor' | 'chlorination' | 'tank' | 'pipe'
  | 'valve' | 'sensor' | 'scada' | 'turbine' | 'gate';

interface EquipmentSpec {
  id: string;
  category: EquipmentCategory;
  name: string;              // «Насос Grundfos NK 200-400»
  vendor: string;
  model?: string;            // ключ к GLTF-ассету, если есть точная модель
  position: [number, number, number];
  rotation?: [number, number, number];
  scale?: number;
  // характеристики
  metrics: {
    capacity?: number;       // м³/ч
    power?: number;          // кВт
    efficiency?: number;     // 0..1
    recovery?: number;       // % (для мембран)
    cost?: number;           // капзатраты
    lifespanYears?: number;
  };
  // порты для потоков
  ports: { in?: string[]; out?: string[] };
  // с чем совместимо для замены
  compatibleWith: EquipmentCategory[];
  status?: 'ok' | 'warn' | 'fault'; // из телеметрии IoT
}

interface TwinModel {
  objectId: string;          // связь с ObjectDetailPage
  name: string;
  shell: { asset?: string; bbox: [number, number, number]; type: 'wtf'|'pumping'|'dam'|'canal' };
  equipment: EquipmentSpec[];
  flows: FlowEdge[];         // граф связей: fromPort → toPort, kind: 'water'|'power'|'data'
  alternatives: Record<string, EquipmentSpec[]>; // варианты замены по категории
}
```

Карточки оборудования переиспользуют существующий каталог (`/catalog`, `CatalogDetailPage`) — «замена технологии» = выбор из каталога совместимых позиций.

## 3. Технология рендеринга (three@0.170 + R3F v8)

### 3.1 Ассеты
- Формат **glTF 2.0 + Draco** (сжатие геометрии) + **KTX2/Basis** (текстуры). Загрузка через `useGLTF` (drei) с `DRACOLoader`/`KTX2Loader`.
- **Гибридный подход к «высокополигональности»:**
  - Точные модели (насосы, мембранные стойки, турбины) — реальные GLTF-ассеты (закупка/моделирование в Blender), LOD 2–3 уровня.
  - Типовые элементы (трубы, каркас, резервуары) — **процедурная генерация** из данных (`TubeGeometry` по кривой, `CylinderGeometry`, `BoxGeometry`) → меньше ассетов, легче менять.
- **Инстансинг** (`InstancedMesh`) для повторяющихся элементов (болты, секции труб, ряды мембран).

### 3.2 Полупрозрачность и разрезы
- Оболочка: `MeshPhysicalMaterial` с `transmission`, `thickness`, `roughness`, либо простой `transparent + opacity` для производительности.
- **Clipping planes** (`renderer.localClippingEnabled = true`, `material.clippingPlanes`) — интерактивный «разрез» здания по слайдеру плоскости.
- Режим wireframe оболочки для «рентген»-вида.
- Слой оборудования всегда непрозрачен и читаем сквозь полупрозрачную оболочку.

### 3.3 Потоки и функционирование
- Анимированные частицы вдоль `CatmullRomCurve3` (насос→фильтр→мембрана→резервуар): shader-driven или `Points` с обновлением `t`.
- Цвет/скорость потока = нагрузка/расход; красный пульс = авария (status: fault).
- Вращение рабочих колёс насосов/турбин при status='ok'.

### 3.4 Взаимодействие
- Raycast по оборудованию → выделение (эмиссия/outline через `postprocessing` OutlinePass или drei `<Outlines>`), всплывающая HTML-карточка (`<Html>` drei).
- Панель «Заменить» → dropdown совместимых позиций из `alternatives` → мгновенный своп меша + пересчёт метрик.

## 4. Движок эффектов (замена → результат)

Замена оборудования пересчитывает агрегаты станции:

```ts
// суммарная производительность = min по «узкому месту» цепочки потока
// энергопотребление = Σ power по активным узлам
// recovery/качество = произведение по ступеням очистки
// капзатраты = Σ cost заменённых узлов
// Δ индексы (благополучие/экология) = f(прирост мощности, снижение энергии, качество воды)
```

Результат отображается: (1) дельта-бейджи на панели станции, (2) визуальное изменение потоков, (3) связь с `/simulator` — апгрейд оборудования двойника = апгрейд узла в Живой модели региона.

## 5. Производительность

- LOD + frustum culling (R3F автоматически); `InstancedMesh` для повторов.
- Draco/KTX2 сжатие; ленивая загрузка ассетов по требованию.
- `<Suspense>` + скелетон-заглушка; ограничение DPR (`gl={{ dpr: [1, 2] }}`).
- Отдельный чанк только на маршруте `/twin` (уже lazy).
- Бюджет: ≤ ~300k треугольников в кадре на средней станции, целимся в 60fps desktop / 30fps mobile.

---

## 6. Связь с IoT / телеметрией

- `EquipmentSpec.status` и живые метрики берутся из IoT-слоя (`/iot`, Supabase realtime / `useAlertNotifications`).
- Датчики на модели подсвечиваются по значению (зелёный/жёлтый/красный).
- Аварии из `/alerts` → пульсация соответствующего узла на двойнике.

## 8. Пайплайн ассетов (как получать «настоящие» модели)

1. Моделирование в **Blender** (или закупка на Sketchfab/готовые CAD → ретопология).
2. Экспорт glTF → сжатие **gltf-transform** (Draco + KTX2): `gltf-transform optimize in.glb out.glb`.
3. Именование по `EquipmentSpec.model`; хранение в `public/models/twin/`.
4. LOD-варианты (`_lod0/_lod1/_lod2`).
5. Реестр ассетов `src/data/twin/assets.ts` (model-ключ → путь + метаданные).

## 9. Риски и ограничения

- **Вес ассетов** — строгий бюджет + ленивая загрузка + сжатие обязательны.
- **Пин three@0.170 / R3F v8** — проверять совместимость drei-хелперов (Outlines, Html, useGLTF) под v9/v8.
- **Точность моделей** — начинать с процедурных приближений, точные GLTF добавлять инкрементально по важнейшему оборудованию.
- **Mobile-производительность** — упрощённый режим (меньше частиц, LOD-даунгрейд, отключаемые потоки).
